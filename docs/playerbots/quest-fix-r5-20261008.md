# Quest fix R5: item sources and game object looting (sim run R5)

Change (`src/server/game/Bots/BotQuest.cpp`):

1. Classifier: an item objective counts as sourced when the quest supplies the item itself (`StartItem` or `ItemDrop1..4` with enough count), or a creature drops it (as before), or a chest game object that has at least one spawn holds it in its loot table. Items that only exist in a chest without spawns return `OBJECTIVE_UNSUPPORTED`; items with no source anywhere stay `MISSING_ITEM_SOURCE`.
2. Looting: new task kind `loot`. The bot picks the nearest spawn of a source object, walks there, interacts and takes the quest item. Already looted or not spawned objects are skipped (per bot `GoIgnore`), then the next spawn is tried. A respawn wait (`GO_RESPAWN_WAIT`, 60 to 600 s) and a busy back-off (`GO_BUSY`, 180 s) are per-bot blacklists, not reach codes, so they never feed the quarantine. A global claim per spawn (150 s, plus a cooling period after a loot) keeps many bots off single-spawn objects. Real failures reuse `ITEM_NOT_DROPPING` (12 min or 8 attempts), `NO_TARGET_SPAWN` and the travel codes.
3. New log reasons: `QUEST_LOOT_GO` (target chosen), `QUEST_LOOT_OBJECT` (item looted, with `item`, `amount`, `count_before`, `looted_total`), `QUEST_LOOT_SPAWN_EMPTY` (spawn not usable, with the cause), blocked codes `GO_BUSY` and `GO_RESPAWN_WAIT`.

Startup index line now reports 304 quest items in chest objects with 5159 object spawns.

## Method

R4 and R5 use the same ramp (300 bots, +5 every 30 s up to 700). Compared on equal 60 minute windows from the start of each ramp (R4 events 2025158 to 2385303, R5 events 6461507 to 6903033). The R4 note was based on the whole R4 log, which ran longer, so the table below uses the R4 window for like-for-like numbers and quotes the R4 note where it differs. The 141 quests are the "never accepted" list of the R4 coverage note.

The combined "accepted among the 227" figure is not reported: the R4 scope list of 227 was not kept, and a rebuild from the world DB did not reproduce it. What is measured is that 55 of the 141 never-accepted quests were accepted (47 rewarded), and that distinct quests accepted at quest level 10 or lower went from 68 to 121 in equal 60 minute windows. Eight quests accepted in the R4 window were not accepted in the R5 window (382, 383, 1499, 1516, 1517, 5623, 92516, 93319); each had only 1 to 3 accepts in R4, and in R5 they were blocked by QUEST_LEVEL, QUEST_PREREQ or path codes, so this looks like ordering noise, not displacement.

### Deaths (open flag)

Deaths rose from 459 to 960 (bots that died 138 to 236; deaths per reward 0.33 to 0.41), stuck events 657 to 888, path failures 250 to 399, while total events rose 360k to 441k and rewards 1,404 to 2,346. The rise appears in every start zone (Durotar 271 to 379, Tirisfal 29 to 172, Elwynn 42 to 161, Teldrassil 27 to 95) with a different killer mix, which fits bots doing more quests and fighting more. No death record mentions a loot task in its recent decisions, and only 3 deaths follow a loot event within 90 s. Attribution is inconclusive: the increase is real, mostly in line with activity, and not tied to the loot task by the data, but the caller should treat deaths as not yet proven neutral.

### Error spam

No new crash dump (6 before, 6 after). The `MoveSplineInitArgs::Validate ... _checkPathLengths()` console line exists in both runs: R4 console 109,990 lines over about 11 hours, R5 console 16,938 lines in the first 70 minutes. Rate is the same order (about 10k and 14k per hour); no new message type seen, not compared line by line.
